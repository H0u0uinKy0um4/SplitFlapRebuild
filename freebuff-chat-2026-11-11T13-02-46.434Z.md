      # Split-Flap OS
      
      A Home Assistant custom integration for a split-flap display driven by the
      ESP32-C3 RS485 **SplitFlap Master** firmware. It replaces the older `splitflap`
      integration with a Home Assistant native app engine, a sidebar panel, and a
      tuning/calibration workbench.
      
      > 🇨🇿 Český návod pro začátečníky: [README.cs.md](README.cs.md).
      
      The integration talks to the master over MQTT. The master keeps ownership of the
      RS485 bus and the slave modules; Home Assistant owns text layout, apps, playlists,
      auto-detected board geometry, tuning state, and persistence.
      
      ```
      Home Assistant                         ESP32 master                 Slaves
      ┌───────────────────────────┐  MQTT    ┌──────────────┐   RS485     ┌────────┐
      │ Split-Flap OS integration │ ───────> │ command/*    │ ──────────> │ module │
      │ engine + apps + panel     │ <─────── │ status       │ <────────── │ module │
      └───────────────────────────┘          └──────────────┘             └────────┘
      ```
      
      ## Features
      
      - **Sidebar panel** (`Split-Flap OS`) with Control, Apps, Tuning, and Settings
        tabs, plus a live flap preview.
      - **Board auto-detection**: module count comes from the master status payload.
        45 modules become 3×15 and 64 become 4×16. Small displays use a single row.
        The physical frame can be overridden with rows/columns and a per-row module
        layout such as `3,3,1`.
      - **Physical layouts and app availability**: short rows are centred, module IDs
        are assigned in reading order, and data apps are disabled with a reason when
        every row is not wide enough.
      - **Apps** rendered from Home Assistant data where possible:
        clock, date, dashboard, weather, stocks, crypto, NHL scores, MBTA transit,
        countdown, world clock, ISS position, and colour animations.
      - **Playlists** with per-page text, loop control, and saved named playlists.
      - **Animation send orders**: left-to-right, right-to-left, columns, centre-out,
        outside-in, diagonal, random, rain, and spiral.
      - **Tuning UI** for module inspection, home, goto, relative steps, home offsets,
        EEPROM position maps, recording drum indexes, bus scan, sync, and refresh.
      - **Entities and services** so automations can send text, launch apps, and run
        hardware actions without the panel.
      - **Character validation**: text and playlists are checked against each
        module's reported `flap_list` before anything is sent; a missing flap raises
        an error naming the module and character.
      - **Czech localization** of the setup/options flow and service names; the panel
        and entity names remain English.
      - **Backup/restore** of settings, playlists, and the last module snapshot.
      - Only one config entry is allowed, matching the single-master firmware.
      
      ## Requirements
      
      - Home Assistant 2024.11 or newer.
      - The MQTT integration configured and connected to the broker used by the master.
      - SplitFlap Master firmware with these topics:
        - status: `<prefix>/status` (retained, JSON)
        - commands: `<prefix>/command/display`, `sync`, `scan`, `update`, `calibrate`
      - The default prefix is `splitflap`. It is configurable during setup.

      3. Restart Home Assistant.
      4. Go to **Settings → Devices & services → Add integration → Split-Flap OS**.
      5. Enter the MQTT topic prefix (`splitflap` by default) and a display name.
      
      ### Manual
      
      Copy `custom_components/splitflap_os` into your Home Assistant
      `config/custom_components/` directory and restart. Then add the integration from
      the UI.
      
      The sidebar panel is registered automatically; no Lovelace resource entry is
      needed.
      
      ## Panel
      
      - **Control** — live display, multi-line compose box, colour insert buttons,
        start column, send order, speed, playlist builder, and saved playlists.
      - **Apps** — tap an app to start it; the gear opens the settings that app reads.
      - **Tuning** — module matrix, per-module diagnostics, motor home/goto/step,
        record and position-map controls, and a clickable character map.
      - **Settings** — grouped settings (display, weather, markets, sports, transit,
        time, animations), hardware actions, backup/restore, and connection details.
      
      The panel uses Home Assistant WebSocket commands and does not require a build
      step. It is loaded from `frontend/splitflap-os-panel.js` through `panel_custom`.

      ## Services
      
      All services live under `splitflap_os.*`.
      
      | Service | Description |
      | --- | --- |
      | `send_text` | Send wrapped text with `start`, `style`, `speed`, `stop`, `raw` |
      | `play_playlist` | Play pages with `delay` and `loop` |
      | `start_app` / `stop_app` | Control the app engine |
      | `sync` / `scan` / `update` | Hardware state actions |

      | `save_playlist` / `delete_playlist` / `run_saved_playlist` | Playlist management |
      | `set_settings` | Merge and persist settings |
      
      Service `pages` fields accept a real YAML list when called from scripts, or a
      JSON array string when using the UI. `send_text` treats `start` as a 1-based
      column offset. `speed` is forwarded with the display command; the current master
      firmware ignores it and uses its own fixed bus timing.
      
      Before text is published, every module that reports a `flap_list` is checked
      for the characters it will receive. If a flap is missing, the service raises an
      error naming the module and character, and nothing is sent. `play_playlist`
      validates all pages before it starts. Padding spaces are ignored, and modules
      without a reported flap list are skipped because there is no drum to compare
      against.
      
      ## Settings

      available from the panel. Important keys include:

        automatic layout. `rows` and `cols` are the frame dimensions; `0` means

      - `timezone`, `units`, `page_delay`.
      - `weather_entity` (preferred), `zip_code` + `weather_api_key` (OpenWeather

      - `stocks_list`, `crypto_list`, `sports_teams`.

      - `anim_effect`, `anim_style`, `anim_speed`.

      selected, so no external API key is required for the normal path. Stocks and
      crypto use Yahoo Finance and CoinGecko respectively. MBTA works without a key at

      ## Physical layout and app availability
      
      The layout describes the real display, not just the number of modules.
      
      ```text
      row_counts = 3,3,1     frame = 3 rows × 3 columns
      
      row 1: module 1  module 2  module 3
      row 2: module 4  module 5  module 6
      row 3:          module 7
      ```
      
      Rules:
      
      - Module IDs are assigned left to right, then top to bottom.
      - A row with fewer modules is centred inside the frame.
      - A layout may leave blank frame cells, up to one row's worth. For example,
        7 modules in a 3×3 frame is valid; 7 modules in a 3×15 frame is rejected.
      - The integration rejects a saved layout that does not match the detected
        module count or leaves too much blank space. If the detected count changes
        later, the panel shows a layout error instead of silently using the wrong
        modules.
      - Text pages and colour animations work on any valid layout, including one
        module. Data apps require every row to be wide enough for their content.
      
      App minimums are declared in `apps/__init__.py`:
      
      | App | Minimum frame |
      | --- | --- |
      | Animations | any size |
      | Clock | 3 × 9 |
      | Date | 3 × 11 |
      | Dashboard | 3 × 11 |
      | Weather | 3 × 10 |
      | Stocks | 3 × 7 |
      | Crypto | 3 × 8 |
      | Sports | 3 × 8 |
      | Metro | 3 × 10 |
      | Countdown | 3 × 12 |
      | World Clock | 1 × 10 |
      | ISS | 3 × 10 |

      the panel or a service returns an error. If a running app becomes unsupported
      because the layout changed, the engine stops it.
      
      ## MQTT contract
      
      The integration expects the master's retained status payload to look like this
      (abridged):
      
      ```json
      {
        "state": "online",
        "text": "HELLO",
        "version": "1.1.0.0",
        "bus_compat": 1,
        "mqtt_compat": 1,
        "compat": 1,
        "modules_count": 45,
        "modules": [
          {
            "id": 1,
            "state": "online",
            "online": true,
            "flap": "H",
            "total_steps": 4096,
            "home_offset": 2832,
            "current_step": 3616,
            "flap_list": " ABC...",
            "map_of_positions": {"0": 2832, "1": 2896},
            "fw_version": "1.0.1",
            "fw_bus_compat": 1,
            "fw_bus_compatible": true,
            "fw_compat": 1,
            "fw_compatible": true
          }
        ]
      }
      ```
      
      `version`/`bus_compat`/`mqtt_compat` are the master's own version contract;
      `compat` remains an alias for `mqtt_compat` for older integration builds. The
      per-module `fw_version`/`fw_bus_compat` come from the slave's `m<id>s` reply;
      `fw_bus_compatible` is omitted when the module does not report a version, and
      `fw_compat`/`fw_compatible` remain aliases for the bus values.
      
      Display commands are sent as an ordered array so the array order doubles as the
      animation order:
      
      ```json
      {"modules": [{"id": 1, "char": "H"}, {"id": 2, "char": "I"}]}
      ```
      
      Calibration commands use `{"module": 1, "action": "goto", "index": 5}` and the
      master translates them to the slave protocol.
      
      Position-map entries with the slave's `0xFFFF` sentinel are treated as unset:
      they are omitted from snapshots, never shown as tuned in the character map,
      and the integration falls back to the estimated flap position. Negative and
      out-of-range entries are ignored in the same way. An explicit `positions`
      object sent to the `calibrate` service may still contain `65535` to clear a
      single entry on the slave.
      
      ## Versions and module firmware
      
      All three parts of the system (slave firmware, ESP32 master, this integration)
      use two independent **compatibility axes** because two different peers talk to
      each other:
      
      | Axis | Peer contract | Carried by |
      | --- | --- | --- |
      | **BUS_COMPAT** | RS485 application protocol and the OTA/bootloader entry contract | slave + master |
      | **MQTT_COMPAT** | MQTT status/command JSON schema | master + Home Assistant |
      
      The master bridges the two, so it carries both numbers. Each repository also
      has its own release inside those generations, and the published version is
      composed from the numbers that apply to it:
      
      ```
      slave    <bus>.<release>              1.0.1      bus 1, release 0.1
      master   <bus>.<mqtt>.<release>       1.1.0.0    bus 1, mqtt 1, release 0.0
      HA       <mqtt>.<release>             1.0.8      mqtt 1, release 0.8
      ```
      
      | Where | Version | Compatibility | Read from |
      | --- | --- | --- | --- |
      | Home Assistant integration | `1.0.8` | MQTT `1` | panel header, connection info, WebSocket `version`/`mqtt_compat` |
      | ESP32 master | `1.1.0.0` | bus `1`, MQTT `1` | status `version`/`bus_compat`/`mqtt_compat`, connection info |
      | Slave application | `1.0.1` | bus `1` | panel module inspector, firmware card, `m<id>v`, UPDI dump |
      
      The integration compares the master's `mqtt_compat` with `MQTT_COMPAT` in
      `const.py`. A mismatch shows a warning banner, but it never blocks display
      traffic, OTA cancellation or a module reset. If the master predates the version
      protocol, the panel says the version is unknown rather than assuming it is
      compatible. The bus generation is shown for diagnostics; the slave <-> master
      side is not something Home Assistant speaks directly.
      
      The module firmware card shows the application version and bus generation each
      slave reports. Use it to prove an OTA actually took: bump the slave's
      `FW_RELEASE`, upload the new `.hex`, and the card should show the new version
      after the module reboots and re-homes. OTA itself refuses an unknown bootloader
      protocol before writing any page.
      
      When changing the frontend, bump `VERSION` in `const.py`, `manifest.json` and
      `frontend/constants.js`, and every `?v=` import parameter, together.
      `tests/test_versions.py` enforces that lockstep and the major/MQTT_COMPAT
      relationship.
      
      ## Coordinate system and recording index 0
      
      The slave counts `pos` from the hall entering edge. Flap 0 sits at `homeOffset`,
      and the fallback position for an unset map entry is
      `homeOffset + round(index * totalStepsPerRev / 64)`, modulo
      `totalStepsPerRev`. The integration mirrors this when it estimates a flap
      position, so `home_offset` and `total_steps` in the status payload are enough to
      locate any flap.
      
      Recording index 0 is supported: `m<id>r0` stores the current position as
      `map[0]` and redefines `homeOffset`. That is the intended way to re-centre flap
      0, not a destructive compatibility write. Older master firmware also sent a
      second `m<id>w0:0`; current firmware does not.

      ## Troubleshooting
      
      - **Panel says OFFLINE** — check the MQTT integration, the topic prefix, and the
        retained `<prefix>/status` payload. The master sends a heartbeat every 30
        seconds; the integration marks it offline after 90 seconds.
      - **No modules** — press **Scan bus** in Tuning. The status payload's
        `modules_count` drives the board size.
      - **Layout error or disabled apps** — open Settings and adjust the frame or
        row layout. A row layout such as `3,3,1` must describe every detected module
        and may leave at most one row of blank frame cells. Data apps stay disabled
        until every row is wide enough.
      - **Display shows old text after a restart** — the integration restores the last
        known module snapshot and desired characters; press **Sync** to refresh from
        the master.
      - **Service fails with "Cannot display: module ... lacks ..."** — a module's
        reported drum lacks one of the requested characters. Check the module in
        Tuning, use a character from its flap list, or remove it. Nothing was sent to
        the display.
      - **Panel missing after install** — reload the integration once, then hard-refresh
        the browser. Check Home Assistant logs for `panel` or static-path errors.

Home Assistant is an afterthought: it publishes MQTT discovery configs for a text entity, app/playlist selects, a center switch and some sensors.

Yours is the opposite split: **Home Assistant owns layout, apps, playlists, persistence and the UI; an ESP32 master owns the RS485 bus**; MQTT is the contract in between.

That means they aren't interchangeable. On your hardware (ESP32 master + RS485 slaves) the Flask app would bypass the master and need the Pi physically wired to the bus. The two are mutually exclusive owners of the same display.

    Show a field only when other setting values match.
    - format: `{ "other_key": "expected_value" }`
    - multiple keys are combined with AND logic

    Render live derived text in settings:
    - `compute`: compute function name in frontend registry
    - `watches`: keys that trigger recomputation

    "compute": "polling_rate_stats",
    "watches": ["polling_rate", "data_source"]
    }
    ```
    ### Inline Toggle Next to Input
    Attach a segmented toggle to a text/number field via `inline_toggle`:
    ```json

    "key": "search_radius_unit",

    "position": "after",
    "size": "md"
    }
    }
    ```
    `inline_toggle` keys:
    - `key` (required): setting key persisted alongside the main input
    - `options` (required): string/object option list
    - `default` (optional): default selected option
    - `position` (optional): `"before"` or `"after"` (default)
    - `size` (optional): `"sm"`, `"md"`, or `"lg"`
    ### Declarative Settings Sync
    Use these keys to synchronize related fields:
    - `sync_values` on source field: maps source value to updates for target fields
    - `sync_parent` on child field: parent key to set when child changes manually
    - `sync_parent_custom_value` on child field: parent value to set (default: `"custom"`)
    ```json
    {
    "key": "units_preset",
    "type": "toggle",
    "options": ["aviation", "metric", "imperial", "custom"],

    }
    }

    ```json

    "key": "distance_unit",

    "sync_parent": "units_preset",
    "sync_parent_custom_value": "custom"
    }

Good question to press on — of those six, only **three are real architectural advantages** (1, 2, 3). The other three are product/ops choices, and two of them are weaker than they look. Here is the detailed version, with what each one actually does in their code and what your equivalent does.

## 1. The app ecosystem is a plugin runtime, not a list of apps

**Theirs.** An app is a directory: `apps/<id>/manifest.json` + `app.py`. The server loads every enabled directory at startup:

```python
spec = importlib.util.spec_from_file_location(f"plugin_{app_id}", module_path)
mod = importlib.util.module_from_spec(spec)
spec.loader.exec_module(mod)
_plugin_modules[app_id] = mod
```

and calls a fixed, narrow interface:

```python
pages = mod.fetch(plugin_settings, format_lines, get_rows, get_cols)
```

Three things follow from that, and they're the actual architectural win:

- **Dependency inversion.** The runner doesn't import app modules or know their names. It iterates a registry of manifests. Adding an app is adding data, not editing the runner or the UI.
- **The interface is a capability bundle, not a god object.** `fetch(settings, format_lines, get_rows, get_cols)` means an app cannot touch serial, MQTT, playlists, or engine internals. Your providers receive `engine`, which is more powerful but lets every app couple to the whole engine; that's why your app modules import `Page`, depend on `engine.async_cached`, `engine.http_json`, etc.
- **Per-app isolation at the runtime boundary.** Results are cached per app (`_plugin_caches[app_id]` with `refresh_interval`, overridable by a `polling_rate` setting), and a failing fetch degrades to the last cached pages, or an `OFFLINE` / `APP ERROR` page — the loop keeps going.

**Yours.** `APP_DEFS` is a tuple in `apps/__init__.py` and `APP_PROVIDERS` is a static dict, imported at module load. Adding an app means writing a module, an `AppDef`, `SettingField`s, importing it in `apps/__init__.py`, and adding it to `APP_PROVIDERS`. It is type-safe and testable, but it's a compile-time registry. Nothing external can contribute an app.

**The honest trade.** Their dynamic loading buys extensibility with two real liabilities: `exec_module` on code fetched from a raw GitHub URL (their own comment says "no sandboxing"), with no version pinning, signature, or manifest validation. And `fetch()` is synchronous inside the display thread, so one slow HTTP call stalls the entire board; your `await engine.async_cached(...)` with a per-key lock doesn't. So: **better extensibility model, worse safety and concurrency.** The idea worth stealing is the *narrow provider contract and data-driven registry*, not the arbitrary-code loading.

## 2. Settings are a schema owned by the app, not by the integration

This is the most portable idea in their repo, and it exposes a concrete limitation in yours.

**Theirs.** `manifest.json` declares the settings, and the server normalizes them into a UI schema. Keys are automatically namespaced per app unless declared global:

```python
def _resolve_manifest_setting_key(app_id, raw_key, *, global_key=False):
    if global_key:
        return raw_key
    return f"plugin_{app_id}_{raw_key}"
```

The schema supports things your `SettingField` has no concept of:

- `visible_when` / `disabled_when` — the countdown manifest shows each of its five event/target pairs only when that slot's toggle is on, and shows a warning notice when all five are off.
- `sync_values` / `sync_parent` — picking a units preset writes the dependent unit fields, and manually changing a child flips the parent to `custom`.
- `inline_toggle` — a segmented control attached to a text/number field (e.g. radius + mi/km).
- `computed` + `watches` — read-only derived fields recomputed when watched keys change.
- `notice` — non-input warning/info blocks.
- `search_chips` with a `searchUrl` — server-backed pickers, used for timezones.
- Options as `{value, label}` objects, not just strings.

Their frontend is a generic interpreter over that schema; `get_plugin_settings_config()` builds the whole thing server-side, resolving related keys so conditional rules survive namespacing.

**Yours.** `SettingField` is `key, label, type, options, placeholder, default, min, max, step, domain, help`, and `_fieldHtml` understands exactly `select`, `number`, `password`, `datetime-local`, `text`. There is **one flat global settings dict**. `settings_for_ui()` merges only keys in `SETTINGS_KEYS`, and `async_set_settings()` silently drops anything not in that frozenset. That has two consequences:

- Two apps cannot have independent values for the same concept (`clock_format` is shared between Clock and Countdown; `units` is global).
- A future third-party app's settings would be *dropped on save* unless a developer adds its keys to `DEFAULT_SETTINGS`. The schema is not extensible at runtime.

**Why that's architectural, not cosmetic.** In their design the app owns its configuration contract and the UI is a renderer. In yours the integration owns the schema and the app borrows from a global namespace. The first scales to N apps; the second stays consistent only because a human keeps editing one registry. Their cost is a much larger schema interpreter and no type checking; yours is trivially typed and testable.

## 3. Notification interrupts: preemption baked into the page loop

**Theirs.** A queue plus a consume point between pages:

```python
_notify_queue = []
_notify_lock = threading.Lock()

def _pop_notify():
    now = time.time()
    with _notify_lock:
        _notify_queue[:] = [m for m in _notify_queue if m['expires_at'] > now]
        return _notify_queue.pop(0) if _notify_queue else None
```

and in the main loop, after each page's rotation + delay:

```python
if settings.get('notify_enabled', False):
    msg = _pop_notify()
    if msg:
        _show_notify_message(msg)
```

`_show_notify_message()` sends the text with its own animation order, waits for rotation plus `display_seconds`, then returns — and the outer loop simply continues. That's the clever part: because the playlist position lives in the loop's local iteration state, an interrupt **doesn't need to save or restore anything**. The interruption is just a pause, not a mode change.

**Yours.** `engine._runner()` owns mode (`app` / `playlist` / `idle`) and iterates pages; stopping is `_stop_event` + task cancellation. There is no priority queue. A message sent through `send_text` or `async_stop` clobbers `active_app`; you can't overlay "DOOR" on a running clock and resume. Adding the feature correctly in your architecture means an explicit preemption layer: a queue drained in `_runner`, with the current page/app state preserved across the interrupt.

**So is it better?** Their version is simpler *because it is synchronous and single-threaded*. Yours would need more machinery — but it would also be able to interrupt during a slow async app fetch and still stop cleanly on unload. Copy the *queue + resume-point* semantics, not their blocking `time.sleep` loops.

## 4. Deployment ergonomics: not architecture

`setup/install.sh` is a conventional root installer: apt packages, venv, `pip install -r`, two systemd units with `sed`-rewritten paths, `enable`/`restart`, `settings.json` created if missing. `network-check.sh` manages the hotspot through NetworkManager.

That's packaging, and it's better only because their product is **self-contained**: one Pi owns the UI, the logic, the serial port and the network fallback. There's no broker or HA dependency to reach the UI. Your integration deliberately delegates all of that to Home Assistant (HACS install, HA auth, snapshots, updates, remote access, logs). Colocating the control plane is simpler to deploy and worse to operate at scale — no multi-client consistency, no automations, no service layer, and the UI dies with the Pi. This isn't a design you should envy; it's a consequence of their hardware topology.

## 5. Simulation is a transport seam, not a mock

**Theirs** opens the serial port at import and falls back cleanly:

```python
try:
    ser = serial.Serial(SERIAL_PORT, BAUD_RATE, timeout=0.5)
except Exception as e:
    ser = None
    logging.error(f"Serial failed. Simulation Mode. Reason: {e}")

```

Then `send_to_display()` only guards the write:

```python
if ser and not sim_mode:
    ser.write(f"m{i:02d}-{char}\n".encode())
```

Everything else — plugin fetch, caching, playlist timing, rotation estimation, MQTT publish, `/current_state` — runs unchanged. They also expose `sim_rows`/`sim_cols`, `/toggle_sim`, and `hardware_connected`, so the browser can render a full grid without hardware.

**Why that's a good seam.** Hardware access is reduced to one boolean at the edge. You can develop app content without owning a display. It is not a real device simulator: there are no module IDs, no offline modules, no scan, no position feedback. But it's honest about what it fakes.

**Yours** has the same *opportunity* at the MQTT boundary — the coordinator is already the transport — but no explicit fake implementation. Your panel preview renders `display.lines` from the snapshot, which gives visual fidelity, yet with zero modules you can't exercise the full app/playlist loop end to end the way they can. The idea worth taking is a named, swappable transport with an in-memory fake, not their `sim_mode` boolean.

## 6. Calibration: a batch workflow, not better machinery

**Theirs.** The tuning state is exposed as three values per module per character, which is the enabling design:

```python
positions[mod_str] = {
    'expected': expected,                    # from calibrations
    'tuned': int(tuned) if tuned is not None else None,
    'active': int(tuned) if tuned is not None else expected,
}
```

`/auto_tune` then supports `home`, `goto_char` (send the same character to every module), `adjust` (apply a delta to the tuned map and write `mNNw<idx>:<val>`), and `get_positions`. That makes "put the whole board on flap N, nudge it, write it" a single flow. `/custom_tune` adds goto/save/erase per module.

**Yours** is more correct about position semantics (the `0xFFFF` sentinel, index-0 redefines `homeOffset`, `position_known`, OTA), but tuning is per-module; there's no first-class "expected vs tuned vs active across the whole board at one character" model. Their `mNNc` calibration route also blocks the HTTP request for up to 45 seconds, which is worse engineering. So this is **a workflow advantage produced by keeping calibration data explicit**, not a superior calibration architecture.

## The summary that matters

Their six wins are bought with one big simplification: an 84 KB module with module-level mutable globals and threads, where `active_app`, `active_app_playlist`, `current_playlist`, `last_sent_page`, `stop_event` and `settings` are all shared state. Features are cheap to add because everything can reach everything. Your architecture is the opposite trade: explicit state, one engine loop, a snapshot contract, a coordinator that owns MQTT, pure layout/positions modules, and tests that enforce the version axes.

So the genuinely instructive differences are:

1. **App contract**: narrow capability interface + data-driven registry vs a static typed registry.
2. **Settings ownership**: per-app namespaced declarative schema vs one global whitelisted dict — this is the one place their model is structurally ahead.
3. **Preemption**: a queue with a resume point in the loop vs no interrupt layer at all.
4. **Transport fake**: an explicit simulation seam vs none.

Everything else — installer, hotspot, 40 content apps, batch tuning — is either packaging or content, and does not require their architecture to replicate. You could add 1–4 to your engine without giving up typing, tests, OTA, layout correctness, or the MQTT contract.
